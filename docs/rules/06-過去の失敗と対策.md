## 10. 実際に起きた失敗と、その再発防止（2026-08-11）

本節は「起きた失敗」「原因」「二度と起こさないための仕組み」を対にして記す。
**気をつける、注意する、といった心構えは対策として認めない。仕組みで防げない対策は書かない。**
同じ対策は1か所へ集約し、既存の対策で防げた失敗では規約を増やさず、その対策を自動化する。

### 10.1 手元では通るのに自動検査（CI）が落ちる／出所の違う成果物を見た

- **起きたこと**: CIが2回連続で失敗した。1回目はテストが読む作品ファイルをコミットし忘れ、2回目はアプリ本体が、リポジトリに含めない `verification/` のファイルを参照していた。
  また、棚上げした未完成の作品ファイルで折り鶴を実機確認し、「鶴に見えない」と報告したが、その展開図は鶴のものですらなかった。
- **原因**: `scripts/check.ps1` は未コミット・無視対象を含む作業フォルダ全体を使うが、CIはコミット済みの内容だけを使う。検査や判断に使う入力の出所を確かめていなかった。
- **仕組みでの対策**:
  - `scripts/check-ci.ps1` で**コミット済みの内容だけを取り出した複製**にCIと同一のコマンド一式を通し、push前フック `scripts/hooks/pre-push` でも自動実行する。
    `scripts/check.ps1` の全5検査合格だけを根拠にpushしない。
  - テストやアプリ本体から `.gitignore` 対象（`verification/`、`scratchpad/`、`vendor/` など）を読み込まない。fixtureは `crates/*/tests/fixtures/` に置いてコミットし、調査用の一時コードを製品側へ残さない。
  - テスト入力・画面確認・報告の根拠は `git ls-files` で追跡対象か確かめ、未追跡・棚上げ中のファイルを判断材料にしない。

### 10.2 委譲の切れ目にエージェントが止まる

- **起きたこと**: Codexの完了後、Claudeが検査等の間に次を指示せず、稼働0となり、利用者の「進んでるか確認して」で発覚した。
- **原因**: 「報告を受ける → 検査する → コミットする → 次を指示する」という直列の手順にし、検査とコミットを空白時間にした。
- **仕組みでの対策**: 現在の監視・稼働0・安全な先行投入の正本は§4と、追跡対象の `scripts/watch-agents.ps1` とする。同scriptは報告書・許可sourceを10分ごとに見て40分無更新を通知し、process情報は補助表示するだけで停止・変更しない。

### 10.3 Codexが本体リポジトリのgitを操作しかけた

- **起きたこと**: CI再現用の複製で `git checkout` が本体側で実行されかけた。書込み拒否で未遂だったが、成功すれば他担当の変更が消えていた。
- **原因**: 「複製先で操作する」とだけ書き、「本体では一切のgit操作を禁止する」と明記しなかった。
- **仕組みでの対策**: 作業担当のgit禁止は§1を正本とし、複製・検証の指示には本体 `C:\Users\oltot\Documents\git-projects\ORIGAMI3\.git` へのcheckout / commit / stash / reset禁止を実パスで記す。

### 10.4 折り図の読み解き資料どうしが矛盾していた

- **起きたこと**: 悪魔の手順25で、`anchors.md` は動きを `C→A`、`part-025-064.md` は `C→B` と記していた。矛盾に気づかず実装を6回試み、すべて失敗した。
- **原因**: 資料を作った時点で相互の突き合わせをしていなかった。
- **仕組みでの対策**: 折り図の読み解き資料に基づく実装は、該当箇所を原資料の画像で確認し、資料間の矛盾を先に検証する段階を指示に入れる。矛盾があれば実装前に報告させる。

## 10.5 「合格」と報告する前に、成果物と形を自分の目で確かめる（2026-08-12・17・28）

- **起きたこと**:
  1. 1分ローズを「完成」「裂け0.0」と繰り返し報告したが、利用者が手順書PDFを開くと、
     面が交差した塊でバラの形ではなかった。Claudeは3D画像を一度も見ていなかった。
  2. 「紙の裏表と重なりの正しさと表示の整合性は確認しながら進めること」と
     指示されていたのに、担当の「実機確認は未確認」を受け入れ、
     利用者の画面へ壊れた表示を再び出した。作業ツリーに複数担当の変更が混ざり、
     どの変更の証拠にもならない状態が続いていた。
  3. 折り鶴を「裂け `1e-6` 未満・自己交差0」だけで受け入れ、
     両翼先端の距離 `1.625064657e-15`、独立した先端3/4本、
     完成時の重なり順の一般制約違反16件・破棄31組でも長期間「合格」とした。
     正しい伝承折り鶴と比べると、折り目は68/102本欠落、余分21本、
     山谷が逆12本、面の一致0/31だった。
- **原因**:
  - エージェントの報告と `max_seam_gap` の数値を成果の確認の代わりにした。
    共有辺が離れない値は、面が突き抜け、形が全く違っても0になり得る。
  - 合格条件の妥当性と検査の実体を確かめなかった。
    悪魔には担当判断の自己交差検証が9箇所あったがローズは0箇所で、
    鶴では§10.5の「形の条件」自体が自動化されていなかった。
  - 混ざった作業ツリーの画像を証拠にできないという正しい理由を、
    確認できる状態を作る代わりに未確認を了承する理由にした。
- **仕組みでの対策**:
  - `crates/ori3-layers/tests/work_shape_contract.rs` が `crates/*/tests/fixtures/` の作品を
    共通走査し、新しい作品も自動で対象にする。受け入れ条件には
    `self_intersection_pairs` が空であることと、外形・高さ・対称性・層の重なり順など
    **形の条件**を必ず含める。
  - 正解の展開図がある作品は、頂点・辺・山谷・面の不一致が各0であることを検査する。
    折り鶴の正解は
    `crates/ori3-layers/tests/fixtures/traditional-crane/traditional-crane-cp.ori3` で、
    利用者から受け取った `traditional_crane_math_bundle/` と座標差0で一致することを確認済みである。
  - 正解が無い作品は、①全内部頂点の平坦条件
    （角の交互和が等しい／山と谷の本数差が2）②独立した先端の本数
    ③先端間距離が0でないこと④凸包の面積と周長⑤左右対称性を全て検査する。
    「裂け」と「自己交差」だけを受け入れ条件にしない。
  - 重なり順の一般制約は完成まで全ての手で検査し、工程ごとの違反数を表で出す。
    鶴で鳥の基本形までを見た0件は、首・尾・頭で5→17→14→16件へ増えた。
  - 受け入れ検査の `#[ignore]` は、理由文に未達の実測値と外す条件を必ず書く。数値の無い `#[ignore]` を合格扱いしない。
  - Claudeは「完成」「合格」と報告する前に成果物の画像を自分で開き、
    画像を見ていなければ「未確認」と明記する。PDF等の資料も中身を開き、
    ファイルサイズや生成成功だけを根拠にしない。
  - 3D表示・重なり順・展開図の適用・手順再生に触る変更は
    「画像で確認済み」でなければコミットしない。「未確認」なら、
    `git worktree add <リポジトリ外の一時パス> HEAD` で変更を1件だけ含む作業ツリーを作る。
    混ざった作業ツリーの画像は証拠にしない（§10.1）。
  - 3D表示に触る並行担当は1件までとする。同時に2件以上が触ると、どちらも実機確認できなくなる。
  - 実機確認は毎回、①3D canvasからUI overlayを除外し、紙の面だけについて
    `裏 / (表 + 裏)` を数え、各成分を画像で目視する
    ②`surface_rank` が面番号順（`[0,1,2,…]`）でないこと
    ③重なる面のすき間から求めた上下と `surface_rank` の一致
    ④重なり順最上面がその画素へ描かれること⑤以上を画像で目視、
    の5項目を同じ条件で行う。旧条件の証拠は未追跡の
    `scratchpad/live-capture-report.md` にあるが、このパス自体を規範の実体にしない。

## 10.7 コミットと証拠の扱いで実際に起きた失敗（2026-08-12）

### 10.7.1 差分を読まずにコミットし、コミット済みの内容で組み立てられなくなった

- **起きたこと**: `git diff --stat` の行数だけを見て、まだ取り込んでいない作業にしかない項目
  `motion_path` を参照する1行を混入させた。手元では通ったが、コミット済みだけでは組み立てられなかった。
- **原因**: §7の「`git diff` の実際の差分を読む」を `--stat` で代用した。
- **仕組みでの対策**: コミット前に `git diff --cached` の中身を全て読む。
  ほかに未コミット作業がある場合は `git worktree add <一時パス> HEAD` で
  コミット済みだけの作業ツリーを作り、複製の全検査（5〜6分）の前に組み立てて混入を検出する。

### 10.7.2 `git checkout --` で他の未コミット作業を巻き添えにした

- **起きたこと**: 自分が書いた誤ったテストを取り消すため `git checkout -- <ファイル>` を実行し、同じファイルにあった別の未コミット変更も消した。
- **仕組みでの対策**:
  - `git status --porcelain` の変更件数が0でなければ `git checkout -- <ファイル>` を使わず、
    自分が足した部分だけを編集で取り除く。
  - 大きな未コミット作業を抱えたまま作業しない。棚上げするなら、パッチと未追跡ファイルをリポジトリ外へ保全してから作業ツリーを綺麗にする。

### 10.7.4 測る前に原因を断定した／混雑した測定を基準にしかけた（2026-08-13・28）

- **起きたこと**:
  - やっこさんで「1本を4°動かすと他が179.9°動く」ことを欠陥としたが、
    分割数1/4/64の全てで同じ場所へ収束する幾何的に正しい挙動だった。
    根拠の無い「30°以内」のテストも足して撤回した。
  - #18（規約上の実測1,332秒）を最適化ありで走らせ、
    CPU 6,759秒・経過2時間55分でも終わらず外から停止した。
    同時に別担当3件が `cargo` を実行しており、未コミット変更のせいと断定しかけた。
    画面テストが混雑で7件落ち、単独では全て通った例もある。
- **原因**: 仮説なら変わる量を変えておらず、測定値と同時実行数も同じ記録に残していなかった。
- **仕組みでの対策**:
  - 原因を報告する前に、その原因なら変わるはずの量を1つ変えて測る。変わらなければ原因ではない。未コミット変更を原因とする前に、変更前を同じ混雑度で測る。
  - 性能・決定性の値には、同時に走る**ほかの** `cargo` / `rustc` /
    テスト実行ファイルの数を同じ行へ記録する。その数が0でない値は基準にせず取り直す。
  - 合格条件の数値は実測を根拠にし、実測値と余裕を取った境目を同じコメントに残す。実測の無い数値を条件にしない。
  - 測定が上限の3倍を超えたら打ち切って実測値を報告し、終わるまで待たない。

### 10.7.5 変えたcrateのテストだけで合格と判断した（2026-08-13）

- **起きたこと**: `ori3-rigid` のソルバーで、折り角の目標との差を
  「+180°と−180°は同じ折り方」と丸めた。`cargo test -p ori3-rigid` は通ったが、
  `ori3-layers` の `preliminary_base_folds_the_square_into_four_layers` が壊れ、
  複製の検査まで気づかなかった。
- **原因**: §7の `scripts/check.ps1` をcrate単位のテストで代用した。
  また、角度の丸めが山折りと谷折りの区別を消し、途中の形と記録済み重なり順を裏返した。
- **仕組みでの対策**:
  - §7の全体品質ゲートを通す。`scripts/hooks/pre-commit` は `.rs` または
    `Cargo.toml` / `Cargo.lock` を含むコミットで、§10.6 #18〜#21の4件を `--skip` した
    `cargo test --workspace` を自動実行し、失敗時はコミットを止める。
    `scripts/install-hooks.ps1` がpre-commitとpre-pushを有効化する。
  - 角度の等価性を扱う変更は平坦な終点だけでなく途中の姿勢も検査する。`assert_display_order` は99%まで折った上下を見て、この誤りを実際に捕まえた。

### 10.7.6 通常テストが追跡対象や基準記録を書き換えていた（2026-08-13・28）

- **起きたこと**:
  - 悪魔の受け入れテストが `crates/ori3-layers/tests/fixtures/devil-025.ori3` を毎回上書きし、
    数値の最終桁 `1e-14` が変わった。同じファイルを `folded_query.rs` と `step_oracle.rs` が
    読むため実行順でも内容が変わった。折り鶴も
    `apps/desktop/src/lib/__fixtures__/crane.json` を毎回上書きしていた。
  - 提案完成度 `0.4326478860317622` は、一般制約2/37違反・破棄5組の
    実際の紙では起こり得ない重なりで測られていた。折り鶴も前川定理を3/15頂点で満たさず、
    書込み前検査が無ければ欠陥を記録へ焼き付けるところだった。
- **原因**: 「fixtureや記録を作る」と「それで検査する」を同じテストが兼ね、書込み前の物理検査も無かった。記録は測った結果であって、正しい結果とは限らない。
- **仕組みでの対策**:
  - 通常テストは記録を読んで照合するだけにする。歴史上の書込み口は
    `#[ignore]` の `regenerate_crane_front_fixture` / `ORI3_DEVIL_FIXTURE_OUT` だったが、
    後者は現HEADに存在せず、現在の仕組みとは扱わない。
  - 作品ファイル以外の基準値も同じ扱いにする。新しい書込み口の設計条件は、
    `#[ignore]` の再生成専用テスト1つ、固定出力先、専用環境変数
    （例 `ORI3_REGENERATE_TASK24_RECORD=1`）が無ければ即時失敗、である。
    この専用テストは現HEADに未実装なので、自動化済みとは報告しない。
  - 再生成は書込み前に、裂け `1e-6` 未満／自己交差0／
    重なり順の一般制約違反0・破棄0／全内部頂点の平坦条件／
    同じ入力で10回連続bit一致を全て通す。1つでも未達なら書き込まず失敗する。
  - 書込み直前に元の内容と一致することを確かめ、失敗時は元へ戻す。再生成後は旧値・新値・理由・日付を同じコメントに残す。
  - `scripts/check.ps1` は `cargo test --workspace` の前後で
    `git status --porcelain --untracked-files=no` を比較し、追跡対象が1つでも変われば失敗する。

### 10.7.7 計算結果・実測値・小数を環境非依存の期待値として扱った（2026-08-13・17）

- **起きたこと**:
  1. `apps/desktop/src-tauri/src/store.rs` の
     `flat_fold_notice_does_not_stop_the_requested_motion` は、8本を180°まで送った
     計算結果に通知の期待値を結び付け、CIでは自己交差0組・通知なしで落ちた。
  2. `surface_rank_agrees_with_the_measured_gap_without_using_the_crease_rule` は
     `checked >= 50` に手元の実測値を使い、手元50・CI49の1本差、余裕0で落ちた。
  3. `crease_patterns_stay_identical_to_the_recorded_baseline` は展開図文字列を完全一致で比べ、
     座標の最下位1桁（実測 `1.11e-16`）で落ちた。同じ入口で2回続けてCIを落としたが、
     v0.4.5リリースの同じ入口で2回続けて落ち、主張自体ではなく数値の決め方が原因だった。
- **原因**: 完全に折った状態の近くでは浮動小数の丸めで解が計算機ごとに変わる。
  `scripts/check-ci.ps1` は手元と同じ計算機であり、
  コミット済みだけの検査と別CPUでの合格は別である。
  「期待値」だけを禁じたため、下限件数や文字列一致ならよいとも読めた。
- **仕組みでの対策**:
  - solve結果に期待値を結び付けない。通知・判定規則は角度や交差を引数で明示し、
    計算を通す検査は「操作が止まらない」「有限値が返る」など環境不変の性質にする。
  - 実測値を下限・上限へそのまま使わず、実測と余裕を取った境目をコメントに残す。
    既存例は実測の約8割で、`robust_stacks >= 4_000`（実測4888）、
    `>= 1_000`（実測1298）、`checked >= 40`（実測50/49）である。
  - 個数・つながり・種類・IDは完全一致でよいが、計算で出た座標・角度は許容差付きで比べる。許容差の根拠（実測のずれ、別物と区別できる最小距離）を同じコメントへ残す。
  - 同型を1件だけ直さず、`assert_eq!` / `assert_ne!` を全数走査して総数と修正数を報告する。
    この修正では未発火の同型1件も見つかった。同種走査の共通規律は§10.7.8に集約する。
  - `check-ci.ps1` の合格を「CIに通る」と報告しない。CIが落ちたらログ受領まで推測で直さず、
    push後にGitHubの結果が緑になったことを確認する。緑なら指示を待たず次へ進む。

### 10.7.8 関係する量と同種箇所を全数で比べず、同じ場所を3回直した（2026-08-13）

- **起きたこと**: 3Dで見えないはずの折り目について `depthTest` だけを3回直した。1回目は5材質中1つ、2回目は残り3つを直しても解決しなかった。
- **原因**: 強調表示の太さ `0.006`（`HIGHLIGHT_RADIUS`）と、紙の重なり全体 `0.001`（`MAX_STACK_RATIO`）・層間隔 `0.0002` を並べなかった。強調線は全厚の6倍太く手前の紙を貫通するため、深度設定では消えない。カメラの奥行き範囲（手前0.01・奥100）で区別できる細かさとも比べなかった。
- **仕組みでの対策**:
  - 見え方の修正前に大きさ・間隔・許容差・分解能を同じ単位の表にし、桁を比べる。
  - 同じ役割・同じ欠陥の形が他に無いか、材質・分岐・呼出し・検査表現を全数走査する。「全部でいくつ、そのうちいくつを直したか」を報告する。
  - 画面を拡大して自分の目で見るまで「直った」と報告しない。このときは拡大して初めて別の面の縞模様にも気づいた。目視の共通条件は§10.5に従う。

### 10.7.11 組み立て先・複製の数え漏れと誤削除（2026-08-20・21・26）
