## 1. 役割分担

- **実作業はすべて作業担当（Claudeのサブエージェント）が行う。** 実装、レビュー、デザイン、GUI操作、スクリーンショット撮影、資料の読み取り、PDF作成、環境の調査と修復を含み、作業の種類を理由に例外を作らない。
- **Claudeは次の6つだけを行い、自分で成果物を作らない。** ①実名と数値を含む指示書の作成、②成果物と差分の確認、③品質ゲートの実行、④git操作、⑤アプリの起動と終了、⑥利用者への報告と `docs/報告記録.md` への記録。「自分でやったほうが速い」は委譲しない理由にならない。
- Claudeが直接実行してよいコマンドを次に限定する。表に無いコマンド、特に `cargo` と `npm` は直接実行せず、組み立て、検査、原因切分け、一覧作成も担当へ委譲する。

- 実機確認は、担当が `npm run tauri -- build --no-bundle` で作った**画面同梱版だけ**を使う。`cargo build` はdebug/releaseとも `localhost:1420` の `devUrl` を見る非同梱版なので使わず、指示書に `cargo build -p desktop --release` や「アプリの起動方法」節を書かない。統括は担当から実行ファイルの実パスと組み立てコマンドを受け取り、同梱版だと確認できなければ起動しない。
- 担当への指示書には必ず次を書く。

  ```text
  アプリの起動と終了は統括が行います。あなたは起動しないでください。
  昇格承認を求める必要もありません。
  組み立てが終わったら、実行ファイルの実パスと組み立てコマンドを報告してください。
  ```

- 報告は会話だけで終えない。`scripts/check-report-log.ps1` が記録の存在・形式・日付順・本文・`apps/` / `crates/` の最新コミット日との関係を検査し、`scripts/hooks/pre-commit` が製品変更と同じコミットの記録を要求し、`scripts/check-release-ready.ps1` がリリース日の記録を第5検査として確認する。
- 理由: 役割を分けないと確認者が不在になる。利用者がサブエージェント利用を3回指示した後もClaudeが `cargo check --workspace`、`cargo test -p desktop --lib`（失敗2件）、原因切分けと一覧作成を続けたため、許可範囲を実名で固定した。報告を会話だけに置いたときも、判断・原因・実測値・未確認事項が流れ、同じ調査を繰り返した。

## 2. Claudeサブエージェントの起動と使い方

- Agentツールで起動する。サンドボックス区分（read-only / workspace-write）に相当するものは無く、代わりに指示文（prompt）へ**「gitへの書き込み禁止」「触ってよいファイルの限定」**を明記し、割り当てたgit worktreeのルート（絶対パスが `%TEMP%` 配下でもよい）も指示文で明示する。作業ファイルだけを非worktreeの一時フォルダへ移して起動しない。可能な限り複数エージェントを並列で起動するが、工程・検査・品質を省かない。各指示には触ってよいファイル、触らないファイル、担当重複の無い範囲を実パスで明記する。
- モデルは**判断・設計・原因究明・競合解決はopusまたはgpt-5.6-sol、単純な作業・機械的な置換・待機・集計はsonnetまたはgpt-5.6-terra**を選び、起動ごとに選んだモデルと理由を1行で記録する。Codexのsol/terra使い分けは、利用者の明示指示を根拠とする。
- 作業担当にcommit、push、checkout、merge、stash、reset等のgit書込をさせない。特に本体 `C:\Users\oltot\Documents\git-projects\ORIGAMI3\.git` を禁止対象として明記し、変更内容と対象ファイルだけを報告させる。統括は実行後に `git diff` / `git status` でgit未書込を確認する。
- 投入時に、そのworktreeの `git rev-parse HEAD`、未コミット件数、対象検査のベースラインを記録する。全体検査は絶対値だけでなく「着手時から悪化していないこと」で判定し、本体に無い既知の赤を担当へ直させない。この基準が無かったため、古い未コミット分だけに `crates/ori3-layers/tests/acceptance_frog.rs:1450` の `clippy::neg_cmp_op_on_partial_ord`（`if !(gap < GAP_LIMIT)`）が残るworktreeで `cargo clippy --workspace -- -D warnings` が失敗した一方、本体の同じ形は0件だった。§10.7.8の既知欠陥形ラチェットも同じベースラインを機械検査する。
- 理由: 作業場所の誤認、共有変更の衝突、`.git` 書込失敗、worktreeごとの世代差を、開始前の実測で切り分けるため。Codexが使える状況に戻ったときは、本節の区分（モデルの使い分け・gitへの書込禁止・触ってよいファイルの限定）がそのまま当てはまり、次のコマンドで起動する。

```text
codex exec --model gpt-5.6-sol -c model_reasoning_effort=ultra --sandbox workspace-write --skip-git-repo-check - < 指示ファイル
```

## 3. 作業担当へ渡す指示の書き方

- 粗い依頼は禁止する。Agentツールのprompt引数に渡す指示書には必ず次の7項目を含める。
  1. 対象のファイルパスと関数名を、略称でなく実名で記す。非コード作業も「該当なし」と理由を書く。記載前に統括が `rg` または `grep` で実在を確かめ、コマンドと出力行を指示書へ貼る。貼れない実名は書かない。
  2. 合格条件を数値で記す（例: 「平らに畳めない点の警告が0」「裂けの量が `1e-6` 未満」「16層で200ms以内」）。
  3. 変更・起動・緩和してはいけないものを列挙する。
  4. 作業を段階に分け、各段階で中間報告を義務づける。具体値を変更させる前に現在値を報告させ、別worktreeならHEAD・未コミット件数・実測値も先に確認する。
  5. 関係する過去の失敗例と、その原因を記す。
  6. 使用可能な道具について、コマンド、対象、確認方法まで具体的に記す。
  7. 成果物の保存先パスを明記する。
- 達成単位は小さく区切り、「144手順すべて」のような大目標を1回で依頼しない。担当が「前提が違う」と編集前に止めたら正しい対応として扱う。
- 実在確認を省いた結果、`CompletionTolerance::DEFAULT` を `plan.rs` と誤記した（実体は `crates/ori3-propose/src/search.rs:348`）。また `[6,4,15]` を `[1,4,15]` へ変える指示を14面版へ出したが、実際の先端列は `[10,6,3,1,4,13]` で、経路は固定59面の作品を直接読んでいた。いずれも担当が書込前に止めたため実害0だった。
- 理由: 大きく曖昧な依頼、存在しない実名、古い現在値は、合格の自己判断、無効な作業、過去の失敗の再発を招くため。

## 4. 委譲後の停滞監視

- 委譲と同時に、報告書と担当が触ってよいソースを `scripts/watch-agents.ps1` の監視対象にし、完了まで**10分間隔**で最新更新時刻を見る。稼働エージェント数も数え、残作業があり、既存成果の検査を待たず安全に進められる非重複の次作業があるのに0件なら、検査・commit・報告より先に次を投入する。
- 指示書に「成果は報告書ファイルへ書く」と記す。サブエージェントは完了すると統括に完了通知が届くが、統括は通知を待つだけでなく報告書ファイルの更新時刻を直接見る。Codexでは応答待ちが7,200秒で3回切れても担当は継続していたため、通知の有無だけに進行判定を委ねない。
- 「プロセスが生きている」「CPUを使っている」だけでは進行と判定しない。同scriptは40分更新が無ければ停滞を通知し、`cargo` / `rustc` / test process数・CPU時間・`CommandLine` を補助表示するだけで、process停止やファイル変更はしない。
- 継続監視は担当ごとに `active` / `stalled` / `unmonitorable` と、同じ停滞episodeでは変わらず成果更新時に失効するincident IDをruntimeとlatest outputへ発行する。`scripts/hooks/check-agent-watch.ps1` は監視processの完全な起動引数、定義、担当別状態、件数、hash、出力、監視対象の現在値を独立に再照合し、監視が実行されていない、壊れている、古い、または自己矛盾している場合は委譲をfail-closedで拒否する。
- `stalled` または `unmonitorable` が1件でもある間、統括が新しく委譲する本文の先頭には、現在の全incident IDそれぞれについて次の宣言を1回ずつ置く。未知・古い・重複・一部不足のID、空の `evidence` / `next`、引用やcode fence内だけの記載では通らない。停滞を直すための確認・再委譲も同じ宣言を付ければ通るため、修復経路を閉じない。

  ```text
  [AGENT_WATCH_RESPONSE schema=1]
  incident=<64hex>
  action=investigate|continue|reassign|stop-request|complete-check
  evidence=<実測または判断根拠>
  next=<次に行うこと・再確認条件>
  [/AGENT_WATCH_RESPONSE]
  ```

- `action=continue` は `next=progress-when:<何が起きれば進捗とみなすか>` の完全形を必須とする。正常な長時間build、意図的な停止、誤判定をCPU値などから自動判別せず、統括が観測条件を明記して判断する。機械が証明するのは「現在のincidentへaction・evidence・nextを宣言した」ことまでであり、実際に読んだ、理解した、根拠が真である、宣言どおり行動したことは証明しない。
- 停滞や異常は利用者が気づく前に検知し、原因確認、指示の縮小・修正、再委譲を行う。
- 理由: 返信・プロセス・CPU・ファイル更新のどれか1つだけでは、空回りと長時間検査を区別できないため。
